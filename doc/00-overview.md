## 0.2 비전

깃허브 정적 블로그 배포 방식의 근본적 불편함은 "글 하나 올리려고 레포를 열고, 파일을 만들고, 커밋 메시지를 쓰고, 푸시하고, 빌드를 기다리는" 마찰입니다. Oxipage는 이 마찰을 CLI 한 줄, 혹은 AI 에이전트에게 던지는 말 한마디로 줄이는 것을 목표로 합니다.

동시에 이것은 단순한 블로그 엔진이 아닙니다. 개발자·작가·독자·시네필로서의 여러 자아를 하나의 "로비"에 모으고, 각 자아가 각자의 확장(Extension)으로 독립적으로 성장할 수 있는 구조를 만듭니다. 그리고 이 구조 자체를 남들도 가져다 쓸 수 있는 셀프호스팅 오픈소스 제품으로 일반화하는 것을 장기 목표로 둡니다.

## 0.3 핵심 설계 원칙

1. **CLI-first, API-native.** CLI가 하는 모든 일은 인증된 REST API 호출입니다. CLI는 API의 "레퍼런스 클라이언트"일 뿐이며, 별도의 숨은 기능을 갖지 않습니다. 이 원칙 하나로 "API 지원"이라는 요구사항은 자동으로 충족됩니다.
2. **로비(Lobby) + 확장(Extension) 모델.** 코어는 최대한 얇게 유지하고(인증, 미디어 저장, 검색, 스케줄러, 확장 레지스트리), 프로젝트/블로그/소설/영화/책/스크랩/활동/링크 같은 실제 기능은 모두 "확장"으로 구현합니다. 확장은 켜고 끌 수 있고, 각자 자기 데이터 모델·라우트·CLI 서브커맨드·백그라운드 잡을 가집니다.
3. **1인 오너, 그러나 일반화 가능한 구조.** v1은 "인스턴스당 소유자 1명"을 전제로 설계합니다(계정 시스템을 단순화). 다만 이는 멀티테넌트 SaaS로의 확장을 막는 결정이 아니라, "각자 자기 인스턴스를 셀프호스팅한다"(Ghost, Plausible류 배포 모델)는 방향으로 일반화합니다. 서버 하나가 여러 남의 사이트를 서빙하는 구조는 설계 범위에서 명시적으로 제외합니다.
4. **Zero-ops 지향.** 기본 DB는 SQLite, 배포 산출물은 정적 프론트엔드가 내장된 **단일 Rust 바이너리 하나**가 기본 단위입니다. Apple `container`/Docker 컨테이너는 *선택적* 포장 방식이며, 기본 실행 모델은 바이너리를 launchd(macOS)·systemd(Linux)로 직접 기동하는 것입니다. 별도의 DB 서버, 별도의 오케스트레이션 없이 Mac mini 한 대(또는 임의의 단일 Linux 호스트)에서 돌아가야 합니다.
5. **점진적 확장 가능한 인터페이스.** v1의 확장은 컴파일 타임에 링크되는 Rust crate입니다(현실적인 1인 개발 속도를 위해). 하지만 `Extension` trait 경계를 처음부터 "남이 설치 가능한 플러그인"을 염두에 두고 설계해서, 나중에 WASM 컴포넌트 기반 런타임 로딩으로 갈아탈 여지를 남깁니다.
6. **OKLCH 기반 디자인 토큰, 다크/라이트 기본 지원.** 색은 전부 OKLCH로 정의하고, 명도(L) 축만 뒤집어 다크/라이트를 만듭니다.
7. **이중언어는 확장에 따라 "구조적 지원" 또는 "선택적 지원".** 포트폴리오(프로젝트) 확장은 EN/KO 필드를 스키마 레벨에서 강제하지만(전 세계에 보여줄 포트폴리오이므로), 블로그·소설·스크랩은 언어를 자유롭게 선택하되 번역본을 서로 연결할 수 있는 정도로만 지원합니다.

## 0.4 용어

| 용어 | 의미 |
|---|---|
| **코어(Core)** | 인증, 미디어 저장, 검색 인덱스, 스케줄러, HTTP 서버, 확장 레지스트리를 제공하는 최소 런타임 |
| **확장(Extension)** | 하나의 기능 도메인(블로그, 영화 리뷰 등)을 캡슐화한 모듈. 자기 DB 테이블, API 라우트, CLI 서브커맨드, 프론트엔드 라우트를 가짐 |
| **로비(Lobby)** | 사이트 첫 진입 화면. 활성화된 확장들을 요약 카드로 모아 보여주는 허브 |
| **레이아웃 모드(Layout Mode)** | 로비에서 각 확장을 어떻게 배치할지 — `canvas`(둥둥 떠다니는 형태) / `grid`(카드) / `list`(정갈한 리스트) |
| **오너(Owner)** | 이 인스턴스의 유일한 계정 주인 (v1은 1 인스턴스 = 1 오너) |
| **시리즈 그룹(SeriesGroup)** | 해리포터, 반지의 제왕처럼 여러 영화/시리즈를 묶어 별도의 통합 평점·리뷰를 매길 수 있는 단위 |
| **스크랩(Scrap)** | 해커뉴스/긱뉴스 등 외부 글을 저장하고 짧은 코멘트를 붙이는 항목 |
| **Oxipage CLI** | 이 시스템 전용 커맨드라인 도구 (예시 바이너리명 `oxipage`) |
| **스킬(Skill)** | oh-my-pi 같은 AI 코딩 에이전트가 읽어서 CLI 사용법을 익히는 `SKILL.md` 문서 |

## 0.6 v1 범위 밖 (Out of Scope)

의도적으로 뒤로 미루는 것들입니다. 지금 손대지 않는다고 명시해 두는 것 자체가 설계입니다.

- **멀티테넌트 SaaS** (서버 하나가 여러 명의 사이트를 서빙) — "각자 셀프호스팅" 모델을 유지
- **댓글/방명록 등 소셜 기능** — 정적 스크랩·리뷰 위주이므로 별도 확장으로 나중에 고려
- **실시간 협업 편집** — 1인 오너 전제이므로 불필요
- **에피소드 단위 TV 시리즈 리뷰** (시즌/에피소드 세분화) — `movies` 확장은 영화·TV쇼를 "작품 단위"로만 다루고, 프랜차이즈 묶음(`SeriesGroup`)만 지원
- **WASM 플러그인 런타임의 완전한 구현** — v1은 컴파일 타임 확장. WASM화는 리서치 스파이크로만 02/01에 방향성만 남김
- **콘텐츠 개정 이력(revision history)** — 블로그·소설 등의 발행 후 수정 이력 보존. v1은 마지막 상태만 저장하지만, `*_revisions` 보조 테이블 확장 여지를 남겨둡니다.

## 0.7 왜 이런 이름 규칙을 쓰는가

문서 파일명은 영문(ASCII)으로 통일했습니다(`00-overview.md` 등). 실제 저장소가 git으로 관리되고 여러 OS/도구를 오갈 것을 고려한 선택이며, 문서 본문 언어와는 무관합니다.
